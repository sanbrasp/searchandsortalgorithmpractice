# SearchAlgorithmPractice.Tests

xUnit tests for the `SearchAlgorithmPractice` project's `LinearSearch` and `BinarySearch`
projects.

---

## Running the tests

From this directory or the solution root:

```powershell
dotnet test
```

## Test coverage

`LinearSearch` and `BinarySearch` are tested against the same four baseline cases:

- **Hit** — target exists in the collection
- **Miss** — target does not exist in the collection
- **Empty collection** — no elements to search
- **Boundary indices** — target sits at the first or last valid index

`BinarySearch` has an additional pair of tests demonstrating unreliable behavior on
unsorted input (see above).

`Bfs` is tested against six scenarios:

- **Empty graph** — no nodes at all
- **Unknown start node** — start node isn't a key in the graph
- **Single node, no edges** — one node, empty neighbor list
- **Cycle** — two nodes with edges pointing back to each other; confirms termination and no duplicate visits
- **Multiple neighbors** — confirms visit order matches expected FIFO/queue behavior
- **Disconnected components** — confirms BFS from one component doesn't reach an unrelated component

`Dfs` doesn't have test coverage yet.

### Additional Binary Search-specific tests

Binary Search requires sorted input to function correctly, so two extra tests document
what happens when that precondition is violated:

- `LinearSearchTest_FindsExistingElement_WhenArrayIsUnsorted` — confirms Linear Search is
  genuinely unaffected by array order, as expected.
- `BinarySearchTest_MayAccidentallySucceed_OnCertainUnsortedArrays` and
  `BinarySearchTest_MayFail_OnDifferentUnsortedArray_WithSameTarget` — same target value,
  same set of numbers, different arrangement. One "succeeds," one "fails." This pair
  exists to prove Binary Search offers no reliable guarantee once its sorted-input
  precondition is broken — success or failure on unsorted data is coincidental, driven by
  where the target happens to land relative to the algorithm's pivot points.
